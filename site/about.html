The Frame

Two stacks. One pipeline. The GitHub Actions stack we own (11 workflows in a public repo) handles call transcription, ARV math, SMS cadence, Slack scraping, weekly snapshots, dashboard generation, and Blake voice-agent config. The GHL-native workflows stack (38 workflows wired inside the CRM) handles intake forms, missed-call text-back, dead-lead follow-up sequences, SmarterContact ingestion, and the per-event notifications.

Net result. RJ calls people who actually want to talk. Adam reviews instead of doing data entry. Cold leads stop clogging the qualified queue. ARV gets calculated automatically. The team only sees what needs a human decision.

DESIGN RULE

Trust the AI for routing, never for closing. Calls get analyzed, leads get classified, stages get auto-routed when the system is confident — but a deal never moves from LAO → DD → MAO → Contract without a human signing off. The automation handles the noise so humans handle the signal.

01

GitHub Actions — Scheduled Crons

Five workflows run on the GitHub-hosted schedule. Free for public repos. Every run is logged and replayable from the Actions tab.

1a

ACQ Call Recording Automation

EVERY 15 MIN acq.yml → acq_automation.py WRITE

"Find new recordings. Transcribe them. Extract everything that matters. Route the lead. Move on."

Every 15 min, the cron checks GHL for new call recordings on ACQ stages 1-4. Each one runs through Deepgram → Claude → Apify (Zillow + sold comps) → GHL writeback in under a minute. The lead gets its stage auto-routed based on call outcome, 16 custom fields populate, an "APG Lead Summary" note replaces the freeform clutter, and a Rehab Report Google Doc is generated.

Per-recording cost
~$0.04
Deepgram + Claude + Apify, all-in.
Time recovered
~30 min/call
The old job: listen, type, look up Zillow, write summary, set fields.
Coverage
100%
Every recording analyzed. Old workflow caught maybe 10-20%.

Auto-routing logic

  • Hot → Stage 1 → Stage 2 (LAO), creates RJ/Adam tasks (4h due), sets Lead Type = "Hot Lead".
  • Warm → stays in Stage 1, Lead Type = "Warm Lead". Still in qualified queue.
  • Nurture → Stage 0 (Unqualified), Lead Type = "Nurture Lead". Silent demotion.
  • Cold → Stage 0 (Unqualified), Lead Type = "Cold Lead". Silent demotion.

Stages 2-4 are never auto-reversed. Once a lead is a real deal, only humans move it. Also exposes a manual-trigger ARV backfill mode (backfill_recompute=true) for reprocessing entire stages on demand.

1b

ACQ SMS Follow-Up + Dashboard Refresh

EVERY 30 MIN sms.yml → sms_followup.py + 5 dashboard scripts WRITE

"The right SMS, at the right time, on the right number — then rebuild every dashboard from fresh GHL state."

The biggest workflow in the repo. Six sequential steps per tick: (1) sms_followup.py walks every active lead, checks the SMS cadence, sends the next message if due, and classifies inbound replies via Claude Haiku. (2) dashboard.py refreshes the Google Sheet. (3) dashboard_html.py regenerates the Follow-Ups page. (4) deals_dashboard.py regenerates the Deals page. (5) The weekly.html shell rebuilds so layout changes ship without waiting for Friday. (6) priority_activity.py aggregates notes + Blake calls + Slack mentions per priority CID. Final step deploys the whole site/ tree to the gh-pages branch.

Reply latency
≤ 30 min
Bounded by cron tick. Webhooks would push this to seconds.
From-numbers
9
8 state-routed primaries + NJ. Secondary swap on touches 4-6.
Pages refreshed
6
Follow-Ups, Deals, Weekly shell, Priorities, plus Sheet + priority-activity JSON.

Reply classifier (Claude Haiku)

  • STOP / hostile → GHL DND on, tag dnd-opt-out, no task.
  • Wrong number → GHL DND on, tag wrong-number, no task.
  • Not interested (polite no) → tag not-interested, no task. Re-touch eligible later.
  • Positive / neutral → RJ callback task with reply text inline.

Status: SMS sends are currently paused per Q2 strategy (Northern NJ MF 5+ pivot). The dashboard-refresh half of this workflow still runs every tick.

1c

APG Slack Scraper

EVERY 60 MIN slack.yml → slack_scraper.py WRITE

"Watch the team chatter. When someone mentions a lead, capture it before it's lost in the channel."

Every hour, the cron pulls new messages from APG Slack channels, locally scores them against the contact index (no LLM call until there's a candidate match — keeps cost down), then sends candidates to Claude for confidence-rated info extraction. High-confidence updates auto-apply to GHL fields; medium-confidence becomes an audit-trail note. Caches resolved user names to slack_users.json and commits the cache back to main with retry-on-race so the weekly job can resolve attributions.

Local pre-filter
~98%
Of messages skip Claude entirely. Keeps cost per match low.
Auto-update threshold
High only
Medium gets a note. Low/none gets nothing. No silent overwrites.
Rate-limit posture
Safe
Respects Slack's May 2025 limits — 15/page, 2s sleep between pages.
1d

Weekly Analysis Snapshot

FRI 10AM ET weekly.yml → weekly_analysis.py WRITE

"Every Friday, freeze the week. Who moved, who stalled, who needs Adam's eyes."

Cron fires at 14:00 UTC every Friday (≈10 AM ET in EDT). Pulls the full ACQ pipeline state, classifies each lead into buckets — ready_contract, ready_mao, advanced, demoted, new, active_no_move, drop_suggest, quiet — and writes a snapshot to weekly/YYYY-Www.json. Commits to main with a 5-attempt rebase-and-push retry loop in case the SMS cron pushed during the run. The weekly.html shell reads whichever snapshot is newest.

Bucket logic is deterministic — same input → same output — so Adam can audit any week's classification by reading the JSON directly.

1e

Market Analysis Refresh

SUN 4AM ET markets.yml → market_analysis.py WRITE

"Every Sunday morning, rerank every state by where APG should be spending marketing dollars."

Pulls free CSV data from Realtor.com Research and Zillow ZHVI (both refresh monthly, so weekly is plenty). Combines with a hardcoded landlord/tenant-tier table to produce a ranked state table for the Markets page. Writes site/markets.json and commits to main with the same 5-attempt retry-on-race as the weekly job. The Markets page reads the JSON on every load.

v1 ships state-level only. v2 (city/MSA drilldown) and v3 (ZIP) are on the roadmap.

02

GitHub Actions — Manual + Webhook Dispatch

Six workflows fired by a dashboard button or a one-off run from the Actions tab. No schedule — they only run when a human (or a dashboard click) asks. Browser holds a personal GitHub PAT in localStorage; never a GHL token.

2a

Add Note to GHL Contact

DISPATCH add_note.yml → add_note.py WRITE

"Adam types feedback under a Priority card — it lands in the GHL contact note within seconds."

Inputs: cid (GHL contact ID), who (Adam / Mido / RJ), body. POSTs to /contacts/{cid}/notes. Fired by the Priorities page's feedback textarea on every deal card.

2b

Apply Slack Suggestion

DISPATCH apply_suggestion.yml → apply_suggestion.py WRITE

"When the Slack scraper finds a medium-confidence field update, this is the button that commits it."

Inputs: cid, field_updates JSON (asking_price, timeline, motivation, reason_for_selling). PUTs to GHL contact custom fields via the direct REST API (the MCP path is bugged for custom fields). Surfaced as an inline button on the Deals page wherever a medium-confidence Slack suggestion exists.

2c

Update Lead Manually

DISPATCH update_lead.yml → update_lead.py WRITE

"Universal escape hatch — find any lead by name or address fragment and patch their fields or move their stage."

Inputs: free-text search ("4704 9th Ave" or "Marlin Smith"), field_updates JSON, and an optional stage dropdown (unqualified / qualified / LAO / DD / MAO / contract / PSA / dispo / follow_15 / follow_3 / dead). Searches GHL by name + address, picks the best match, applies field updates and stage move atomically.

2d

Configure Blake Agent

DISPATCH configure_blake.yml → configure_blake_agent.py WRITE

"Rebuild Blake's 8 GHL-backed tools and PATCH them into the ElevenLabs agent."

Inputs: optional agent_id (otherwise searches ElevenLabs by name "Blake"), and apply=yes to actually PATCH (default is dry-run). Used whenever Blake's tool surface changes — new GHL field, new action, new search shape. Reads the GHL custom-field IDs from APG's location and produces an ElevenLabs tool spec for each.

2e

Configure Blake Post-Call Webhook

DISPATCH configure_blake_webhook.yml → configure_blake_webhook.py WRITE

"Discover or set the ElevenLabs post-call webhook URL."

Inputs: mode = discover (read-only API probe) or apply (set it). Default URL is the Cloudflare Worker endpoint https://acq-automation.mithchell.workers.dev/webhook, which is what receives Blake's post-call transcripts and routes them into KV → vault sync → dashboard. The post-call webhook is a workspace-level setting that isn't exposed in the ElevenLabs UI on every plan tier — this workflow hits the API directly.

2f

One-Off Cleanup (REVIEW-Mike Spam)

DISPATCH cleanup.yml → cleanup_review_tasks.py WRITE

"Remediation script for the REVIEW-Mike task spam from a pre-fix cadence bug."

Inputs: mode = dry-run (default — just logs) or execute (actually delete). Auto-files a GitHub issue if the run fails. Kept as a workflow rather than a one-shot script so the audit trail (who ran it, when, what got deleted) is permanent.

HOW THE TWO STACKS DIVIDE WORK

GitHub Actions owns: anything that needs LLM inference (call analysis, reply classification, Slack extraction), anything that needs external data (Apify Zillow, Deepgram transcription, Realtor.com CSVs), anything that writes a public dashboard, and anything that talks to ElevenLabs.

GHL-native owns: anything that needs to fire instantly on a CRM event (form submit, inbound call, stage change), anything that's pure GHL-to-GHL plumbing (LAO/MAO math, tag housekeeping), and the human-readable notification emails. Neither stack should reach into the other's lane.

Roadmap

▸ Now Building

A/B template testing In Progress

Tag every send with which template variant fired. Track reply rate per variant in the dashboard. After ~200 sends per variant we'll know which copy converts. Foundation for ML-driven copy optimization later.

Predictive lead scoring In Progress

Score every new lead 0-100 before the first call using property + motivation + timeline + market signals. Jeff prioritizes by score. Heuristic version ships now; ML-trained version once APG hits ~50 closed deals as training data.

Cold lead reactivation In Progress

Properties that went Dead 6+ months ago — life events change. Re-touch sequence with property-specific Zestimate updates ("market's up 8% in your area, want a new number?"). Builds on the existing Follow Up cadence with smarter copy.

Auto rehab scope from photos In Progress

Pull listing photos via Apify, send to Claude vision → automatic repair scope per room + a rough $/sqft repair estimate. Replaces ~30 min of manual estimator time per property and feeds straight into the existing Rehab Report doc.

▸ Future

Real-time reply detection Medium

Switch the SMS reply path from 30-min polling to a GHL webhook for sub-second detection. Means Jeff can call back while the seller is still thinking about it.

Calendly auto-booking Medium

When a positive reply comes in, parse the seller's stated availability. Send back a Calendly link pre-filtered to matching slots. Saves Jeff a round-trip.

Multi-language SMS Future

Detect seller's preferred language. Maintain Spanish + Portuguese template tracks for relevant markets (NJ has heavy Hispanic + Brazilian populations).

Voice AI cold caller Future

For "Call Needed" leads with no recording yet — AI voice agent makes the first qualifying call. Only escalates to Jeff if Hot. Tackles the biggest remaining bottleneck.

Cash buyer dashboard Future

Mirror the ACQ deals dashboard for the Cash Buyer pipeline (OH/PA/NJ/AL). Track buyer engagement, last contact, capacity per buyer.

Spend-per-deal analytics Future

Break down Apify + Claude + Deepgram spend per lead. Calculate APG's true cost-per-closed-deal. Tells us which lead sources are profitable.

Construction services pipeline Future

Same call → transcript → analyze flow but for the Construction Services pipeline. Different prompt, different fields, different routing — same infrastructure.
